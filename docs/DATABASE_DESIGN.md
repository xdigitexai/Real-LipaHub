# LipaHub AI — Database Design

> Engine: PostgreSQL 17 · ORM: Prisma 7 · All money: integer minor units (cents)
> Status: v0.1

## 1. Conventions

- `cuid`-style string primary keys generated by Prisma.
- Every row carries `createdAt` / `updatedAt`.
- Soft state machines encoded as string enums (Prisma enums).
- Tenant scoping: org-owned rows carry `organizationId`.
- Indices on every FK plus query-critical columns; unique constraints
  enforce invariants (see §4).

## 2. Entity groups

### Identity
- `User` — email (unique, citext-style lowercased), passwordHash (argon2id), role `ADMIN|BUSINESS|WORKER`, status `ACTIVE|SUSPENDED`, locale.
- `Session` — userId, tokenHash (SHA-256 of opaque token), expiresAt, ip, userAgent.
- `Organization` — name, ownerId, verificationStatus `PENDING|VERIFIED|REJECTED`, verificationNote, country, currency.
- `WorkerProfile` — userId (unique), headline, skills (string[]), country, experienceLevel, availability.

### Marketplace
- `Campaign` — organizationId, title, description, category, status `DRAFT|FUNDED|ACTIVE|PAUSED|COMPLETED|CANCELLED`, budgetMinor, fundedMinor (derived cache, recomputed in-transaction), currency.
- `Task` — campaignId, title, instructions (md), deliverableSpec, category, rewardMinor, slotsTotal, slotsTaken, status `DRAFT|PENDING_FUNDING|OPEN|IN_PROGRESS|COMPLETED|PAUSED|CANCELLED`, geoAllow (string[]), skillsRequired (string[]), evidenceRequirements (string[]), publishedAt.
- `TaskReservation` — taskId, campaignId, amountMinor, status `HELD|RELEASED_TO_WORKER|RELEASED_BACK|PARTIAL`, one per payable publish.
- `Application` — taskId, workerId, message, status `PENDING|ACCEPTED|REJECTED|WITHDRAWN`, unique (taskId, workerId).
- `Assignment` — taskId, workerId, applicationId, status `ACTIVE|SUBMITTED|IN_REVIEW|APPROVED|REJECTED|DISPUTED|CANCELLED`, deadlineAt, unique (taskId, workerId).
- `Submission` — assignmentId, notes, evidence (jsonb: file refs + answers), contentHash (sha256 of normalized evidence, for duplicate detection), status `PENDING|AUTO_VERIFIED|NEEDS_REVIEW|APPROVED|REJECTED`.
- `VerificationRun` — submissionId, checks jsonb, confidence (0–100), verdict `PASS|FAIL|UNCERTAIN`, escalated bool, engine `DETERMINISTIC|AI|HUMAN`.
- `Dispute` — assignmentId, openedById, reason, status `OPEN|UNDER_REVIEW|RESOLVED_WORKER|RESOLVED_BUSINESS|RESOLVED_SPLIT|CLOSED`, resolution.

### Opportunity intelligence
- `OpportunitySource` — name, kind `RSS|HTML|API|MANUAL`, url, config jsonb (selectors/limits), fetchIntervalMinutes, trustLevel `UNTRUSTED|NEUTRAL|TRUSTED`, robotsRespected, enabled, lastFetchedAt.
- `DiscoveredOpportunity` — sourceId, title, description, url, urlHash (unique per source), titleFuzzyHash, requirement jsonb (structured extraction), rewardText, eligibility, geoRestrictions string[], riskScore 0–100, riskBand `LOW|MEDIUM|HIGH|CRITICAL`, riskSignals jsonb, confidence 0–100, duplicateOfId, status `DISCOVERED|EVALUATED|PENDING_REVIEW|APPROVED|REJECTED|PUBLISHED`, publishedTaskId, aiRunId, reviewedBy, reviewNote.

### Finance (immutable)
- `LedgerAccount` — code (unique, e.g. `worker-payable`, `campaign-funds-held`, `platform-revenue`, `provider-clearing`, `withdrawal-clearing`), name, kind `ASSET|LIABILITY|REVENUE|EXPENSE|EQUITY`.
- `LedgerJournal` — kind (typed list), referenceType/referenceId (polymorphic link), idempotencyKey (unique, nullable), memo, postedById (human actor when applicable).
- `LedgerEntry` — journalId, accountId, direction `DEBIT|CREDIT`, amountMinor (always > 0), accountSnapshotCode. DB-trigger-level invariant enforced in service layer: journals are written in one transaction and sum(debits)=sum(credits); entries are never updated or deleted (corrections = reversing journal).
- `FundingRecord` — organizationId, campaignId, provider `MPESA_SANDBOX`, externalRef, amountMinor, status `PENDING|CONFIRMED|FAILED`, idempotencyKey (unique).
- `WithdrawalRequest` — workerId, amountMinor, status `PENDING_REVIEW|APPROVED|PROCESSING|PAID|REJECTED|FAILED`, providerRef, reviewedById, reviewNote.
- `PaymentTransaction` — provider, direction `INBOUND|OUTBOUND`, externalRef, amountMinor, status, payload jsonb, linked journal id.

### AI orchestration
- `AgentRun` — agent, entityType/entityId, status `QUEUED|RUNNING|SUCCEEDED|FAILED|TIMEOUT|UNAVAILABLE`, model, provider, input jsonb, output jsonb, tokensIn, tokensOut, latencyMs, error.
- `AgentEvent` — runId, type, payload jsonb, ts.
- `ModelConfig` — purpose (unique, e.g. `research`, `trust-safety`), provider, model, temperature, maxTokens, enabled — DB-configurable, adapters read this, no hardcoded model ids in call sites.

### Platform
- `Notification` — userId, type, title, body, link, readAt.
- `AuditLog` — actorId, actorRole, action, entityType, entityId, metadata jsonb, ip. Append-only.
- `IdempotencyKey` — key (unique), scope, responseHash, expiresAt — replay protection for API endpoints.
- `RateLimitCounter` — Redis-backed primarily; DB only for audit of blocks.

## 3. Money model (accounts)

```
provider-clearing        ASSET      cash in/out via provider
campaign-funds-held      LIABILITY  funded, unreserved business money
task-escrow              LIABILITY  reserved per published task
worker-payable           LIABILITY  earned, withdrawable worker money
platform-revenue         REVENUE    commission taken
withdrawal-clearing      LIABILITY  approved payouts in flight
```

Example: KES 1,000 funding → Dr provider-clearing / Cr campaign-funds-held.
Task publish (KES 200) → Dr campaign-funds-held / Cr task-escrow.
Approval (KES 200, 10% commission) → Dr task-escrow 200 / Cr worker-payable 180 / Cr platform-revenue 20.
Withdrawal paid → Dr worker-payable / Cr provider-clearing.

## 4. Invariants (enforced by unique constraints + service transactions)

1. One application per (task, worker); one assignment per (task, worker).
2. `urlHash` unique per source → duplicate discovery rows impossible.
3. `idempotencyKey` unique on journals, funding records, withdrawal
   transitions → retries cannot double-post.
4. Journals balance; posted inside the same transaction as the state
   change they accompany (no state without its money move).
5. Task publish requires `campaign funded ≥ reservation` — checked with
   `SELECT ... FOR UPDATE` on the campaign's funds row cache + ledger
   read.
6. Worker balance can never go negative: withdrawal amount validated
   against ledger-derived balance inside the approval transaction.
